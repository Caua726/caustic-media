# Win32 input

Keyboard, mouse, touch, pen and gamepad on Windows — through four unrelated APIs,
because Microsoft added each one separately and never retired any.

```
win32/
  message.cst   WM_* — keyboard, mouse, touch, pen
  rawinput.cst  WM_INPUT — unaccelerated motion, per-device
  xinput.cst    gamepads
  gameinput.cst the modern replacement for XInput
  ime.cst       composition and candidates
  backend.cst   input/source.cst implemented over them
```

Messages arrive through [`window/win32`](../../window/win32/win32.md), which owns
the window procedure; this backend interprets them.

---

## Four APIs, four device families

| | What it covers | Shape |
|---|---|---|
| **Window messages** | keyboard, mouse, touch, pen | `WM_*` delivered to the window procedure |
| **Raw Input** | unaccelerated mouse, per-device keyboards | `WM_INPUT`, registered per device class |
| **XInput** | Xbox-compatible gamepads | polled, flat C, `xinput.h` is 8 KB |
| **GameInput** | everything XInput does, better | the modern replacement |

DirectInput is the fifth and is skipped: `dinput.h` is 123 KB of COM for
functionality XInput and Raw Input cover, and Microsoft deprecated it for
gamepads years ago. Only genuinely exotic joysticks still need it.

---

## Messages are cooked, Raw Input is raw

The message path gives what the user configured: pointer acceleration applied,
key repeat generated by the system, layout translated. `WM_CHAR` delivers
characters, `WM_KEYDOWN` delivers virtual keys, and the two are separate messages
for the same keystroke — which is the scancode/keysym distinction from
[`../input.md`](../input.md) appearing again under different names.

**Raw Input is the mouselook path.** `RegisterRawInputDevices` then `WM_INPUT`
delivers deltas straight from the driver, unaccelerated and unclipped. Combined
with hiding the cursor and clipping it, that is how a first-person camera works on
Windows — the direct equivalent of X11's `XI_RawMotion` and Wayland's
relative-pointer.

Raw Input also distinguishes devices, which the message path cannot: two
keyboards are one keyboard as far as `WM_KEYDOWN` is concerned.

---

## Gamepads: XInput is easy and limited, GameInput is neither

**XInput** is four functions and a struct — `XInputGetState` returns buttons,
triggers and sticks for up to four controllers. Flat C, no COM, trivially bound.

Its limits are real: **four controllers maximum**, Xbox-compatible only, no
access to a controller's gyroscope or touchpad, and it is polled rather than
event-driven. A DualShock connected over USB works, with its extra hardware
invisible.

**GameInput** is the modern replacement — more devices, richer data, proper
hotplug — and it is what a new program should use. It is also newer than a lot of
installed Windows, so XInput remains the compatibility floor.

For what XInput cannot reach, [`hidraw`](../hidraw/hidraw.md)'s Windows
equivalent — HID directly — is the answer, exactly as on Linux.

---

## Text input and IME

`WM_CHAR` handles simple layouts and dead keys. Composition — Japanese, Chinese,
Korean — goes through the **IMM** API and its `WM_IME_*` messages: composition
started, composition string updated, result committed, candidate list changed.

It is more surface than Wayland's `text-input` and less than X11's XIM, and it is
the well-trodden path on the platform where most such users are.

---

## Order of work

Alongside the Win32 window backend, which owns the message pump.

1. **`message`** — keyboard and mouse, the ordinary path.
2. **`xinput`**, which is small and brings gamepads immediately.
3. **`rawinput`**, for mouselook.
4. **Touch and pen** from the message path.
5. **`ime`**, when `ui/` needs a text field.
6. **`gameinput`**, when XInput's limits are reached.
