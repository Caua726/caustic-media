# X11 input

Keyboard, mouse and touch from an X11 session — and from a Wayland session
through XWayland, which is the same protocol and the same code.

```
x11/
  core.cst      KeyPress, ButtonPress, MotionNotify from the core protocol
  xi2.cst       XInput2: multitouch, pen, raw motion, per-device
  keymap.cst    keycode to keysym, modifiers, layout changes
  backend.cst   input/source.cst implemented over them
```

Events arrive through [`window/`](../../window/window.md), which owns the
connection; this backend interprets the `XEvent` structures rather than opening
its own display.

---

## The core protocol is not enough

X11's original input model is three event types and a single master pointer. It
has no concept of:

- **Multitouch.** A touchscreen appears as a mouse, and a second finger appears
  as nothing.
- **Pen pressure or tilt.** A tablet is a mouse with buttons.
- **Multiple devices.** Two mice are one pointer.
- **Raw motion.** Everything is accelerated and clipped to the screen, so
  mouselook cannot work — the pointer stops at the edge.

**XInput2 fixes all four**, and it is `libXi` at 78 KB and 88 symbols — the
smallest dependency in the whole library. It replaces the event types rather than
extending them: `XIDeviceEvent` carries a device id, valuator axes with arbitrary
meanings, and `XI_RawMotion` reports deltas before acceleration.

So this backend is really the XI2 backend, with the core path kept for the
sessions where XI2 is unavailable — which in practice means almost none.

---

## Raw motion, and why it matters here specifically

`XI_RawMotion` delivers unaccelerated deltas with no pointer position at all,
which is exactly what a first-person camera wants. Combined with a pointer grab
and a warp back to the centre, it is how mouselook is done on X11 without reading
`/dev/input`.

That makes X11 the one display server where the cooked/raw distinction in
[`../input.md`](../input.md) can be answered **without** evdev and without extra
permission — worth knowing, because it means a program can have proper mouselook
on X11 with no `input` group membership.

---

## Keycodes are not keysyms, and the mapping changes underneath you

X11 delivers a **keycode**, a number meaning a physical key. Turning it into a
keysym — what the key produces — needs the current keyboard mapping, which the
server holds and which changes when the user switches layout.

`MappingNotify` announces that change, and a backend that caches the table
without watching for it produces the wrong characters after a layout switch, in a
way the user cannot explain.

The distinction is the one [`../input.md`](../input.md) records: keycodes for
WASD, keysyms for shortcuts, and neither is a character.

---

## Text input

The core protocol has `XLookupString`, which handles simple layouts and dead keys
and knows nothing about input methods. Proper composition goes through **XIM**,
an entire protocol of its own, usually served by `ibus` or `fcitx`.

That is a large surface for one feature, and it is worth naming rather than
assuming: a text field that a Japanese user can type into on X11 costs
considerably more than one on Wayland, where the protocol is small and modern.

## Order of work

First backend of the layer, since `window/x11` already exists and already carries
sampled input fields that should become events.

1. **`core`** — interpret the raw XEvent queue `window/x11/` now exposes.
   That queue is already there: `x11.poll_xevent` hands out unmodified
   192-byte events, and `window/` deliberately stopped before deciding what
   they mean.
2. **`keymap`**, including `MappingNotify`.
3. **`xi2`** — raw motion first, since mouselook is what a demo needs.
4. **Multitouch and pen**, when something uses them.
5. **XIM**, only when a text field needs it.
