# X11

Serves X11 sessions and, unchanged, Wayland sessions running XWayland — from a
client's side those are the same protocol, the same library and the same code.
There is no separate XWayland backend and there should never be one.

```

  window.cst           the Window, the ring, the pump, the frame
  surface.cst          presentation: MIT-SHM or the socket
  events.cst           the raw queue and the sampled state
  keys.cst             keycode -> keysym -> a key you can name
  cursor.cst           shape, visibility, capture, relative mode
  wm.cst               fullscreen, maximize, minimize, position, icon
  text.cst             key presses to the text a person typed
```

## What exists

**1163 of the 1168 functions** across seven shared objects, and a window layer
built on top of them.

| | bound | of | excluded |
|---|---|---|---|
| `libX11.so.6` | 770 | 774 | `KeySymToUcs4`, `read_EncodingInfo`, `_Utf8GetConvByName`, `XkbTranslateKey` |
| `libXext.so.6` | 132 | 132 | — (a dozen extensions in one shared object) |
| `libXrandr.so.2` | 70 | 70 | — |
| `libXcursor.so.1` | 61 | 61 | — |
| `libXfixes.so.3` | 37 | 38 | `XFixesFindDisplay` |
| `libXi.so.6` | 82 | 82 | — |

The five exclusions are exported without a leading `_` but declared in no
shipped public header. Binding one would mean inventing a prototype, and a wrong
one is silent corruption, so they are named rather than guessed.

The two defects the previous version had are gone. It is pull-shaped, and the
window hands out a per-frame buffer rather than owning a single surface.

## The abstraction is pull

```cst
while (x11.next_frame(&w) == 1) {
    let is tgt.Target as t = x11.acquire(&w);
    if (t.width == 0) { continue; }
    // draw into t
    x11.submit(&w);
}
```

Three rules, each with a reason:

- **`next_frame` before `acquire`, always.** `next_frame` is where a
  `ConfigureNotify` rebuilds the buffers. `acquire` called first would hand out
  a buffer sized for a window that no longer exists, so without a preceding
  `next_frame` it returns a zero `Target` rather than a stale pointer.
- **Never cache the `Target`.** Under MIT-SHM the buffers genuinely alternate, so
  a cached one writes into a segment the server is reading — visible as tearing
  on the first run rather than as a rare corruption. The mistake is loud on
  purpose.
- **Contents are undefined at `acquire`.** Every swapchain says this. Here it is
  also what lets `submit` swap red and blue in place instead of copying.

## `next_frame` does not always return immediately

The earlier version of this note said it did, and that stopped being true when
MIT-SHM arrived.

`XPutImage` copies synchronously: the call returns and the buffer is free, so
one buffer is enough and there is nothing to wait for. `XShmPutImage` does not
copy at all — it returns before the server has read the shared segment. **Under
MIT-SHM, X11 behaves exactly like Wayland**, and the correct handling is the
same one: two buffers, and a completion event that says when one is free again.

| | socket | MIT-SHM |
|---|---|---|
| buffers | 1 | 2 |
| `acquire` returns | the same pointer every frame | alternating |
| `next_frame` may block | no | yes, if both are outstanding |
| per frame | the whole framebuffer down the socket — 8 MB at 1080p | nothing |
| extra memory | — | one W·H·4 segment, once |

`x11.image_count(&w)` and `x11.transport_name(&w)` report which regime is live.
Not waiting would be the spin-and-hope that [`../window.md`](../window.md)
rejects for Wayland, and it would be no better here.

## MIT-SHM fails asynchronously, and that is the whole difficulty

`XShmAttach` returns True and fails anyway. The real answer is a `BadAccess`
that arrives later, because X errors are asynchronous. A backend that trusts the
return value works on the developer's machine and produces a blank window inside
a Flatpak or a container with a different IPC namespace, with nothing in any
log.

So `surface.cst` installs an error handler, calls `XSync` to force the round
trip, and checks. It costs one round trip once at open and it is not optional.
The other refusals — a remote display, no extension, `shmget` denied — are
cheaper and checked first.

One step that is easy to skip: `shmctl(IPC_RMID)` runs **immediately after
attaching**, not at close. A segment marked that way survives until the last
process detaches, so it stays valid while in use and the kernel reclaims it even
if the process is killed. Deferring it is how a machine accumulates orphaned
segments that only `ipcrm` clears.

### The segment info's address is part of the contract

`XShmCreateImage` does not copy the `XShmSegmentInfo` it is handed. It stores
the **pointer** in the XImage's `obdata`, and every `XShmPutImage` afterwards
reads the segment id back out through it. So the struct has to outlive the call
and never move.

That collides with this layer's own shape, and it took a while to see: `open()`
builds a `Window` in a local and returns it **by value**. With the segment infos
inline in the `Backing`, each XImage captured the address they had inside
`open()`, and the returned copy left every one of them pointing into a dead
stack frame. It worked — a dead frame usually still holds the bytes that were
there — until enough of it had been reused, and then the segment id read back as
zero and the server answered `BadShmSeg`.

What made it hard to place was that it looked like a size bug. The same binary
asking for a 640x480 window worked and a 960x640 one did not, because the two
programs used different amounts of stack before the first present. Two things
finally settled it: printing `&buf[i].seg` beside the XImage's `obdata` — they
disagreed by 10,816 bytes — and the fact that the segment values themselves were
never wrong, only what libX11 was reading through a stale pointer.

So `Backing.buf` is **mapped, not inline**. The ring is mapped for size; this is
mapped for correctness, and the distinction is worth keeping in mind for
anything else whose address escapes into a library.

## Caustic has no unions, and XEvent is one

`XEvent` is a union of 33 event structs sharing a common header, and the union is
spelled as what it physically is: 192 bytes of storage plus one pointer cast per
member.

Caustic structs are packed and C structs are not, so every struct in `bind/`
carries explicit `_padN` fields where the C ABI would have aligned. Those are
load-bearing. Drop the pad after `XConfigureEvent.border_width` and `above`
lands at 68 instead of 72; a resize reads a `Window` assembled from two halves of
two different fields, and nothing says a word.

That is why the numbers are not counted by hand. `tools/x11_layout.c` asks the C
compiler that built this machine's libX11, its output is committed as
`tools/layout.txt`, and `x11_layout_test.cst` asserts **82 struct sizes and 565
field offsets** against it. A missing pad is a failed test rather than a
corrupted frame.

The same mechanism covers `XVisualInfo`, `XWindowAttributes`,
`XSetWindowAttributes`, `XGCValues` and the 44 others.

## Verification

Four tiers, each failing for a different reason.

**Layout.** `x11_layout_test.cst`, ~570 assertions, no libX11 and no server —
which is why it runs in the plain `test` script beside `math/` and `gpu/`.

**Link.** One binary per shared object, each calling every symbol it binds from
inside a branch guarded by a value derived from `argc`. The branch is never
taken, so X is never entered, but the call sites are emitted and `DT_FLAGS =
DF_BIND_NOW` makes the loader resolve every name at `exec`. One transposed letter
and the process dies before `main` — verified by doing it: renaming
`XSetClipRectangles` to `XSetClipRectangels` produced `undefined symbol` and exit
127.

*One binary per soname is not tidiness.* Measured against this toolchain: when a
single binary imports more than roughly 256 distinct extern symbols, `caustic-ld`
emits the PLT relocations for every soname but the `DT_NEEDED` entry for only the
first. Bisected at 240 imports working and 280 not; a binary with 770 imports and
a *single* soname is fine, so it is the second library crossing that line, not
the count alone.

**Coverage.** `tools/check_symbols.sh` compares three sets — what `bind/`
declares, what `tools/symbols.txt` promises, what the local `.so` files export —
and additionally asserts that every declared symbol is exercised by some link
test. That last check exists because the gap opened once already.
`tools/check_constants.sh` does the same for the 348 constants, diffing against
the C compiler's own values rather than against numbers this repository typed.

**Functional.** `x11_test.cst` under Xvfb. The central check is a round trip:
fill a frame with a known pattern, submit, then `XGetImage` our own window and
compare byte for byte — at 640×480, 641×481 and 1023×769, because non-multiples
of four are where an XImage's `bytes_per_line` padding stops matching a naive
`width * 4` stride. That is exactly the failure that produced the banding
recorded in `../window.md`, and running it under both transports is what proves
they agree.

`x11_ext_test.cst` is separate because it genuinely links all six libraries. Its
clipboard test opens **two connections**: a client cannot answer its own
`SelectionRequest` while blocked waiting for the reply to its own
`ConvertSelection`.

## What a program actually links

A window and a frame need `libX11` and `libXext`. Not `libXrandr`, `libXcursor`,
`libXfixes` or `libXi`, even though `bind/` declares all four — the compiler
emits a library import at the **call site** rather than at the declaration, so a
file full of unused externs costs nothing.

**That holds for declarations, not for modules.** Importing a module that
*calls* an extension makes that extension reachable from `main` even when nothing
calls the module, and lazy initialisation does not help because reachability is
decided by the import. So `cursor.cst` and `monitors.cst` are deliberately not
imported by `window.cst` or forwarded by `x11.cst`; a program that wants them
takes them directly, which works because neither knows what a `Window` is:

```cst
use "…/window/x11/monitors.cst" as monitors;

let is monitors.State as mons;
monitors.refresh(&mons, x11.display(&w), x11.root(&w));
monitors.compute_dpi(&mons, x11.display(&w));
```

The price is one `use` line in the programs that want a feature, instead of four
shared-object dependencies in every program that does not.
`tools/check_needed.sh` asserts the result on every CI run.

## Native handles

What Vulkan and EGL need from this backend, and the reason they are public:

```cst
x11.display(&w)   // Display*  -> VK_KHR_xlib_surface, EGL
x11.xid(&w)       // Window    -> the drawable
x11.screen(&w)    // int
x11.visual(&w)    // Visual*
x11.colormap(&w)  // Colormap
x11.root(&w)      // the root window
x11.connection_fd(&w)   // for a program that selects on it
```

`x11.surface_for_gpu(&w, present, user)` builds the `gpu.swapchain.Surface` from
them, which is what lets `gpu/` stay ignorant of `window/`.

Three ABI details that had to be right rather than assumed:

**`XSyncValue` is passed by value.** It is `struct { int hi; unsigned int lo; }`
— eight bytes, which the SysV AMD64 ABI classes as INTEGER and passes in one
general register. So the by-value parameters are `i64`, which is the same
machine convention rather than a shortcut. Twenty of the 38 SYNC functions take
or return one.

**`XdbeSwapAction` is an `unsigned char`,** not an int, and
`XdbeAllocateBackBufferName` takes it by value.

**`XagGetApplicationGroupAttributes` is variadic,** and follows the rule
xlib.cst set for its eleven: fixed arity of trailing `*u8`, callers pass 0, the
callee stops at the first null.

`xext_link_test.cst` calls all 132 behind a branch that never runs, so
`DF_BIND_NOW` makes the loader resolve every name at exec — one transposed
letter and the process dies before `main`. Declaring them costs a binary
nothing: `check_needed.sh` still reports two `DT_NEEDED` entries for a program
that opens a window and draws.

Extensions with no binding at all, and whether this library wants them:

| | symbols | |
|---|---|---|
| **libXtst** (XTEST client) | 29 | for testing input end to end against a real server |
| **libXrender** | 45 | only for an ARGB visual, i.e. a transparent window |
| **libXinerama** | 10 | superseded by RandR, which is bound |
| **libXxf86vm** | 22 | superseded by RandR |
| **libXcomposite** / **libXdamage** | 12 / 7 | for writing a compositor, not a client |

None of those is on the path to a window that draws, which is why none is bound
yet. With libXext and libXss done, the one left worth having is XTEST — it is
what would let the input path be driven against a real server rather than by
building events by hand, which is what text_test.cst does today.

## One connection, many windows

Every Window used to call `XOpenDisplay`, so two windows were two sockets, two
event queues and two copies of every interned atom. They share one now, held by
a refcount that closes it when the last window goes.

The cost is routing: the pump dequeues events for windows other than the one it
was called on, and has to hand each to its owner by `xany.window`. Two bugs in
that, both found by `multi_test.cst`, both worth recording because neither
announced itself:

**Registering the window in `open()` stored a dead pointer.** `open()` builds a
Window in a local and returns it by value, so the address it registered stopped
existing on return — the same lifetime trap as the MIT-SHM segment info above,
in a different place. Registration moved to the pump, which is called with the
caller's real address and self-heals if a Window is moved.

**An event for an unknown window must be dropped, not given to whoever pumped.**
The first version fell back to the pumping window for anything it could not
place. A `ConfigureNotify` for a window that had just closed then resized a
different window — `multi_test` caught it as a 320-wide window reporting 260.
Only an event with no target at all falls back now.

`multi_test.cst` was written against the two-connection version first, on
purpose: a refactor with no regression test is a rewrite.

## A frame count is not a clock

The same mistake three times, in three different tests, and worth writing down
because it looks like waiting and is not.

`next_frame` returns immediately on X11 — there is nothing to pace against — so
`while (n < 40) { next_frame(&w); }` is forty iterations of an empty loop, which
is microseconds. Everything a window manager or another client does is a round
trip through the server: a `_NET_WM_STATE` change, an `XdndStatus` reply, a
selection transfer. None of them has happened yet when the loop finishes.

What that produces is the worst kind of test. It passes almost always, because
microseconds is usually enough for the reply to already be in the queue, and
fails perhaps once in twenty runs — which reads as noise and teaches everyone
to re-run instead of to look.

Every wait in the test files is a deadline in real time now, and the ones that
matter print how long they actually took, so a margin shrinking towards the
limit is visible before it starts flaking again. Measured on this machine: a
fullscreen round trip lands in 0–4 ms against a 5000 ms deadline.

## What is not here

**MIT-SHM's INCR path.** Selections above 1 MB need chunked transfer.
`clipboard.cst` refuses rather than truncating, because a silently shortened
paste is worse than a refused one.

**XI2 valuators.** The pump keeps a raw-motion payload alive for the frame and
counts the events; decoding pressure, tilt and sub-pixel deltas is `input/`'s
job, and `window/` deliberately stops at "the payload survived".

**The wire protocol.** Still the right long-term base — stable since 1987,
reachable over `/tmp/.X11-unix/X0` after parsing the MIT-MAGIC-COOKIE out of
`~/.Xauthority`, roughly 1000–1500 lines for window, events and blitting against
zero dependencies and no libc in the process. It becomes worth doing when the
cost of libc in the address space matters more than the work.

**A generator.** `bind/` was written by hand, with `gcc -E` and `offsetof` as the
source of truth to transcribe from and the test tiers above as the defence
against error. `../window.md` argues for generating it instead; that argument is
still good, and the layout table and symbol manifest are already the shape a
generator would consume.
