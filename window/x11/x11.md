# X11

Serves X11 sessions and, unchanged, Wayland sessions running XWayland — from a
client's side those are the same protocol, the same library and the same code.
There is no separate XWayland backend and there should never be one.

```
x11/
  xlib.cst      the bindings — everything libX11 exposes
  backend.cst   window/device.cst implemented over them
```

---

## What exists today

`window/x11.cst`, 22 of libX11's 774 public functions: open a window, read
events, blit a software frame, close. It works, and the cube example runs on it.

Two things about it are wrong under the decisions in
[`../window.md`](../window.md), and both have to change before a second backend
exists:

- It is **push-shaped** — `while (poll()) { draw(); present(); }` — which is the
  X11 model promoted to interface. The portable API is pull.
- It treats the window as **owning one surface**, which Wayland cannot honour.

Reshaping one implementation is cheap. Reshaping four is a migration.

## The binding surface

| | |
|---|---|
| Public functions | **774** |
| Private `_X*` internals | 407 — not API, deliberately excluded |
| Structs in `Xlib.h` | **168** |
| Constants in `X.h` alone | 349 |

The distribution matters when deciding what to generate first: 170 of the public
functions are the XKB keyboard extension, 69 are colour management, 36 locale, 35
input methods. **Most of libX11 is subsystems a renderer never touches.** The
core — windows, GCs, drawing, events, properties, atoms — is a few hundred.

`libX11` itself is 1282 KB and drags in libxcb, libXau, libXdmcp and **libc
(2135 KB)** — about 3.6 MB, into a project whose identity is not having libc. It
has also been implemented *on top of libxcb* since around 2007, so it is a legacy
façade over the real base rather than the base.

## Caustic has no unions, and XEvent is one

`XEvent` is a union of 33 event structs sharing a common header. The current code
reads it by offset:

```
OFF_TYPE     0     int
OFF_X        64    int    key/button/motion
OFF_Y        68
OFF_STATE    80    modifier mask
OFF_KEYCODE  84    button number shares this slot
OFF_CONF_W   56    XConfigureEvent.width
OFF_CONF_H   60
OFF_CLIENT_D 56    data.l[0]
```

That is compact and it works. It is also **hand-maintained, and a wrong offset is
silent memory corruption rather than a compile error** — which is the single
strongest argument for generating both the structs and the accessors from
`Xlib.h` instead of typing them.

The same applies to `XVisualInfo`, `XWindowAttributes`, `XSetWindowAttributes`
and `XGCValues`, all of which are passed by pointer alongside a value mask.

## Presentation, and why the library helps less than it looks

`XPutImage` **sends the entire framebuffer through the socket every frame** —
1.2 MB at 640×480, 8 MB at 1080p. The cube runs at ~64 FPS at 640×480 that way,
which is tolerable and does not stay tolerable.

The fast path is **MIT-SHM** (`libXext`, present here): a shared memory segment
the server reads directly, so presenting costs a pointer rather than a copy. Both
the library path and the raw-protocol path need it, which means the part that
actually determines performance is work libX11 does not do for you either way.

Under the pull model, `next_frame` on X11 returns immediately — X11 imposes no
pacing, so the client decides. Vsync, if wanted, comes from the GLX/EGL swap
interval or from timing by hand.

## Reaching the protocol directly

The universal base for X11 is the **wire protocol**, stable since 1987 and fully
documented. Confirmed present on this machine: the server listens on
`/tmp/.X11-unix/X0`, and `~/.Xauthority` holds the MIT-MAGIC-COOKIE.

Speaking it costs: connect the unix socket, parse the cookie out of Xauthority,
perform the handshake, then requests are opcode + length + arguments. Estimated
1000–1500 lines for window, events and blitting — against zero dependencies, no
libc in the process, and no 168 structs to bind.

`libxcb` sits between the two: 166 KB, closer to the wire, still drags libc, and
is verbose enough (asynchronous, cookies and replies) that it buys little over
the protocol itself.

The order that follows: **libX11 now**, because it unblocks Vulkan, which is what
proves the native-handle contract. The protocol later, when the cost of libc in
the address space is worth paying down.

## Native handles

What Vulkan and EGL need from this backend, and the reason they are public:

```cst
window.x11.display(&w)   // Display*  -> VK_KHR_xlib_surface, EGL
window.x11.xid(&w)       // Window    -> the drawable
window.x11.screen(&w)    // int
window.x11.visual(&w)    // Visual*
```

## Order of work

1. **Reshape the existing backend** to pull, per-frame buffer and native handles.
2. **MIT-SHM**, once presenting a full frame per socket write starts to hurt.
3. **Generate `xlib.cst`** from the headers, replacing the hand-written 22.
4. **The wire protocol**, if and when dropping libc matters more than the work.
