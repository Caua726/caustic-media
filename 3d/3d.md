# The 3D layer

Content. [`render/`](../render/render.md) knows a mesh handle; this layer is what
turns a file on disk into one, and what animates it afterwards.

```
3d/
  3d.cst        hub
  mesh.cst      vertex data, indices, bounds
  tangent.cst   generating what normal mapping needs and files often omit
  shape.cst     generated primitives: plane, cube, sphere, cylinder, capsule,
                torus, cone, grid
  model.cst     a mesh set plus materials plus a local transform per part
  material.cst  a file's description of a surface, mapped onto render/'s
  skeleton.cst  joints, inverse bind matrices, the pose
  skin.cst      applying a pose to vertices
  anim.cst      keyframe tracks, sampling, blending between clips
  morph.cst     blend shapes
  lod.cst       levels of detail and the distance that selects one

  gltf/         the one that matters          gltf/gltf.md
  obj/          the one you can hand-write    obj/obj.md
  ply/          scans and point clouds        ply/ply.md
  stl/          3D printing                   stl/stl.md
```

Separate from `render/` because parsing a file and evaluating a skeleton have
nothing to do with rasterization, and because `render/` already carries 2D, 3D, a
queue and every resource type.

---

## Formats, in tiers of what they cost

**glTF 2.0 is the one that matters.** It is what the industry converged on for
runtime delivery: PBR materials, skinning, animation, morph targets and
instancing in the specification, exporters from every tool, no licensing
questions. `.glb` is what a program should ship.

**Three that are nearly free**, and worth having for the reach they buy:

| | Cost | What it brings |
|---|---|---|
| **OBJ** | a few hundred lines | universal export, hand-writable while debugging |
| **PLY** | similar | 3D scans and point clouds, the format research tools emit |
| **STL** | less | 3D printing, and a mesh with no topology at all |

**Two that are expensive, and not excluded on principle:**

**FBX** is what game pipelines actually pass around, and it is a proprietary
binary format with no specification. It is not impossible — `ufbx` and Assimp
parse it, so the reverse engineering has been done publicly — it is a
*maintenance commitment*, because Autodesk changes it and nothing obliges them to
tell anyone. Worth doing if a real pipeline needs it, not worth doing on
principle.

**USD** is becoming the interchange standard for scenes rather than models, and
it is a whole composition system with layering, references and overrides, not a
file format. Correspondingly large. Worth watching.

COLLADA is skipped: Khronos deprecated it in favour of glTF, and it exists mostly
in old exports.

## The prerequisite is JSON, and it is smaller than it looks

glTF is JSON with binary buffers, and `std/` has no JSON parser.

But the ecosystem does: **`Caustic/lsp/json.cst` is 365 lines and
`json_write.cst` another 182**, written for the LSP protocol and exercised by it
daily. So the prerequisite is *promoting 547 working lines into `std/json.cst`*,
not writing a parser — a much smaller and much safer job, and one that belongs in
the standard library regardless of this layer.

---

## Where a file's vertices meet a declared layout

[`render/`](../render/render.md) takes **declared** vertex layouts, deliberately
— eleven optional arrays that consumers branch on was the thing rejected. glTF
describes vertices as **accessors**: arbitrary attributes, arbitrary component
types, arbitrary strides, possibly interleaved, possibly sparse.

So this layer's real work on the mesh side is the mapping between them: read what
the file declares, choose the layout preset that fits or build an explicit one,
and convert. A file with three UV sets and two colour channels gets an explicit
layout; a file with position, normal and one UV maps onto a preset and costs
nothing.

That conversion is also where a decision gets made that is invisible later:
whether to keep 16-bit indices when the mesh allows, whether to interleave, and
whether to quantise positions. Each is a real memory saving and each changes what
`render/` receives, so they are options rather than assumptions.

## Tangents are usually missing and cannot be guessed casually

Normal mapping needs a tangent frame per vertex, and most files do not carry one
— glTF makes it optional, OBJ has no concept of it.

Generating one is not merely "compute something perpendicular". The tangent has
to match the convention the artist's tool used when baking the normal map, or
lighting comes out subtly wrong in a way that looks like a bad normal map rather
than a bad tangent. **MikkTSpace is the de facto standard** precisely because
everyone agreeing on one algorithm is worth more than any algorithm's merits, and
glTF names it explicitly.

So `tangent.cst` implements MikkTSpace, and does not invent an alternative.

## Animation

**Sampling** is CPU, always: a handful of interpolations per joint per frame
producing the matrices skinning consumes. Rotation goes through `math/quat`'s
slerp, which exists for exactly this. glTF's three interpolation modes — step,
linear, cubic spline — are all cheap.

**Blending** is what makes animation usable rather than a demo. Walking to
running is a crossfade; aiming while walking is an additive layer over a base
pose; turning only the head is a blend masked to a subtree of joints. A pose is
therefore a value that can be interpolated and combined, not a side effect
applied to a skeleton — which is a small design decision with large consequences
for what is possible later.

**Skinning starts on the CPU.** Correct on every backend, and a CPU-skinned mesh
is an ordinary mesh as far as `render/` is concerned. Moving it into a vertex
stage later changes no data, since the joint indices and weights are already
there.

**Morph targets** are the other half of character animation — facial expression,
muscle bulge, anything a skeleton cannot express. They are per-vertex offsets
blended by weight, which is simple arithmetic on a lot of data, so where it runs
matters more than what it computes.

## Bounds, and the one that is not simple

Every mesh carries an AABB and every model the union of its parts, so culling
assembles from pieces that already exist: `math/geom` has
`frustum_from_matrix`, `frustum_overlaps_aabb` and `aabb_transform` — the tight
transformed box rather than an eight-corner refit.

**A skinned mesh's bounds change as it animates**, and that is a real problem
rather than a detail. The honest options are a conservative box covering the
whole animation, or recomputing per frame from the current pose. Start
conservative and say so: a character that pops out of view mid-animation is a bug
whose cause is very hard to trace back from the symptom.

---

## Materials, and where the mapping is lossy

glTF describes a surface in metallic-roughness PBR: base colour, metallic factor,
roughness factor, normal map, occlusion, emissive, plus extensions for clearcoat,
transmission and sheen. `render/`'s built-in material set is smaller by design.

The mapping is therefore **lossy, and it should be reported rather than silent.**
A model that looks wrong because its roughness was discarded is a frustrating
half-hour; a model that loads with a note saying which channels were dropped is a
decision the program can act on — including by supplying its own shader, which is
the escape hatch `render/` already provides.

---

## Instancing and levels of detail

Both are things a file can carry and a renderer can exploit, and both are cheap
to support once the data is there.

glTF has `EXT_mesh_gpu_instancing` for the first — a mesh drawn many times with
per-instance transforms, which is a forest or a crowd. `render/draw3d` needs an
instanced draw for it to be worth anything, and the two should arrive together.

Levels of detail have no glTF extension worth using, so they come from convention
— a naming scheme, or a program supplying meshes explicitly. `lod.cst` is then
just the distance thresholds and the selection, which is small.

## What is not here

- **Drawing.** A model produces mesh and material handles and hands them over.
- **A scene graph.** A `Model` has internal hierarchy because a file does. That
  is not a world tree, and this layer does not grow one — see the framework
  decision in [`render/render.md`](../render/render.md).
- **Physics and collision response.** `math/geom` answers geometric queries; what
  a program does with a hit is its own business.
- **Textures.** A glTF references image files; decoding them is
  [`image/`](../image/image.md)'s job and uploading them is `render/`'s. This
  layer resolves the reference and passes it on.

## Order of work

1. **`mesh` and `shape`** — primitives, so a scene exists before any loader does
   and `render/` has something to draw that is not hand-written vertices.
2. **Promote JSON into `std/`**, which is the actual blocker and is mostly done.
3. **glTF: static meshes and materials**, plus the accessor-to-layout mapping.
4. **`tangent`**, since normal mapping is the first thing a loaded model wants.
5. **`skeleton`, `skin`, `anim`** — and a pose that can be blended, from the
   start.
6. **OBJ, PLY, STL**, which are an afternoon each once the mesh model is settled.
7. **`morph`, `lod`, instancing**, as programs ask for them.
