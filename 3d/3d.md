# The 3D layer

Content. [`render/`](../render/render.md) knows a mesh handle; this layer is what
turns a file on disk into one, and what animates it afterwards.

```
3d/
  3d.cst        hub
  mesh.cst      vertex data, indices, bounds, tangent generation
  shape.cst     generated primitives: plane, cube, sphere, cylinder, capsule,
                torus, cone, grid
  model.cst     a mesh set plus materials plus a local transform per part
  material.cst  a file's description of a surface, mapped onto render/'s
  skeleton.cst  joints, inverse bind matrices, the pose
  skin.cst      applying a pose to vertices
  anim.cst      keyframe tracks, sampling, blending between clips
  gltf/         the loader
  obj/          the simple one
```

Separate from `render/` because parsing a file and evaluating a skeleton have
nothing to do with rasterization, and because `render/` already carries 2D, 3D, a
queue and every resource type.

---

## Formats

**glTF 2.0, and possibly only glTF.** It is what the industry converged on for
runtime delivery: a JSON scene description with binary buffers, PBR materials,
skinning and animation in the base specification, no licensing questions, and
exporters from every tool. `.glb` — the single-file binary form — is what a
program should ship.

**OBJ second**, because it is trivial to parse and everything exports it, at the
cost of no skeleton, no animation and a material model too weak to map carefully.
It earns its place as the format you can hand-write while debugging.

**FBX is deliberately excluded.** Proprietary, undocumented, and parsing it means
reverse-engineering a binary format that changes between versions of a tool we do
not control.

**A prerequisite, and it is not in the ecosystem yet: JSON.** glTF is JSON, and
`std/` has no parser. It belongs in the standard library rather than here — it is
not a 3D concern — and it blocks this layer's main format.

---

## Where the CPU/GPU line falls

The same rule as everywhere: nothing here is a capability limit, only a placement
decision.

- **Animation sampling** is CPU, always. A handful of interpolations per joint
  per frame, producing the matrices skinning consumes. Rotation interpolates
  through `math/quat`'s slerp, which exists for exactly this.
- **Skinning starts on the CPU.** It is correct on every backend, and a mesh
  skinned on the CPU is an ordinary mesh as far as `render/` is concerned. Moving
  it into a vertex stage later is an optimisation that changes no data — the
  joint indices and weights are already there.
- **Mesh generation and tangent computation** are CPU and one-off.

---

## Bounds, and the one that is not simple

Every mesh carries an AABB and every model the union of its parts, so culling
assembles from pieces that already exist: `math/geom` has
`frustum_from_matrix`, `frustum_overlaps_aabb` and `aabb_transform` — the tight
transformed box rather than an eight-corner refit.

**A skinned mesh's bounds change as it animates**, and that is a real problem
rather than a detail. The honest options are a conservative box covering the
whole animation, or recomputing per frame from the current pose. Start
conservative and say so: a character that pops out of view mid-animation is a bug
whose cause is very hard to trace back from the symptom.

---

## Materials, and where the mapping is lossy

glTF describes a surface in metallic-roughness PBR: base colour, metallic factor,
roughness factor, normal map, occlusion, emissive. `render/`'s material set is
smaller by design.

The mapping is therefore **lossy, and it should be documented rather than
silent.** A model that looks wrong because its roughness was discarded is a
frustrating half-hour; a model that loads with a warning saying which channels
were dropped is a decision the program can act on.

That also argues for the custom-material escape hatch being reachable from here:
a program that wants full PBR supplies its own shader and gets every channel.

## What is not here

- **Drawing.** A model produces mesh and material handles and hands them over.
- **A scene graph.** A `Model` has internal hierarchy because a file does. That
  is not a world tree, and this layer does not grow one — see the framework
  decision in [`render/render.md`](../render/render.md).
- **Physics and collision response.** `math/geom` answers geometric queries; what
  a program does with a hit is its own business.
- **Textures.** A glTF references image files; decoding them is
  [`image/`](../image/image.md)'s job and uploading them is `render/`'s. This
  layer resolves the reference and passes it on.

---

## Order of work

1. **`mesh` and `shape`** — primitives, so `render/` has something to draw that
   is not hand-written vertices, and so a scene exists before any loader does.
2. **JSON in `std/`**, which is the actual blocker.
3. **glTF: static meshes and materials.**
4. **`skeleton`, `skin`, `anim`.**
5. **OBJ**, if it still seems worth it by then.
